# MoneyPilot — PostgreSQL миграция и защита на данните

## Състояние
Това е **тестов клон** за бъдеща постоянна PostgreSQL база. **Не е включен в основния MoneyPilot**. Сегашният сайт използва временен SQLite файл в Render Free.

## Какво е направено
- `postgres/001_initial.sql`: първоначална схема с потребители, сесии, сметки, записи, ограничения, индекси и версия.
- `postgres/db.js`: параметризирани SQL заявки, пул с ограничение на връзките, проверка на DB, заключване при миграции.
- `postgres/build-pg.mjs`: създава PostgreSQL вариант на същите API маршрути, без да променя оригиналния SQLite сървър.
- `Dockerfile.pg`: отделен контейнерен образ за PostgreSQL.
- `postgres/import-export.mjs`: транзакционно въвеждане на потребителски JSON експорт в **празен** целеви акаунт. Отказва, ако целта съдържа записи.
- `.github/workflows/postgres-integration.yml`: проверки с реална временна PostgreSQL инстанция.

## Ограничения на Render
Безплатната Render PostgreSQL база изтича 30 дни след създаване, няма managed backup и е само за тестове. Създадена е `moneypilot-postgres-test` във Frankfurt с дата на изтичане **12 декември 2026 г.** Не я използвай за реална финансова информация.

За действително дългосрочно съхраняване е необходима платена, непрекъснато поддържана база. Според публикуваните цени на Render минималният платен PostgreSQL compute започва приблизително от **$6/месец**, като съхранението и евентуални допълнителни такси са отделно. Провери сумата в Render, преди да се съгласиш с платена промяна.

## Проверка преди включване
1. GitHub Actions всички проверки трябва да са зелени: 9 финансови теста и PostgreSQL интеграционни тестове.
2. Отделен Render staging уебсайт от `feature/postgres-persistence-v1`, с `Dockerfile.pg`, изисква `DATABASE_URL` зададен в **Render Environment** (не в GitHub, не в чата). Ползвай Internal Database URL от страницата на тестовата база.
3. Увери се, че `/health` връща `database: postgres`.
4. С тестови профили провери регистрация, вход, добавяне на сметка, приход/разход, календар, експорт, изход и повторен вход.
5. Рестартирай staging уеб услугата, влез и провери дали записите са същите.
6. Пробвай изтриване и проверка за невъзможен достъп до чужди финансови записи.

## План за прехвърляне, без загуба на данни
**Не сменяй DB директно в съществуващия Render web service.**
1. Извлечи JSON експорт от всеки действителен съществуващ потребител (`/api/export`) преди промяната. Експортът не включва парола/сесия. Ако няма експорт и SQLite сървърът е рестартиран, старите записи може вече да са безвъзвратно загубени.
2. Направи архив на наличния SQLite файл, ако е достъпен от първоначалния сървър. Не извършвай автоматично разрушителни операции.
3. Създай и настрои платена PostgreSQL база едва след одобрена цена и план за резервни копия.
4. Направи пълен `pg_dump` след първоначалната проверка на схемата.
5. Стартирай PostgreSQL staging версия, създай нов потребител със същия имейл и после импортирай JSON в празния акаунт:
   `node postgres/import-export.mjs ./user-export.json user@example.com` (изисква `DATABASE_URL`).
6. Сравни брой сметки, записи, суми, дати и Safe-to-Spend преди/след. Не мигрирай автоматично сесиите и паролите; потребителят създава нов профил.
7. Провери регистрация, вход, данни след рестарт, календар, финансови инструменти, мобилен изглед и права на потребителите.
8. Изпълни контролирано превключване на основната услуга едва след зелени тестове и работещ план за връщане.

## Резервни копия и възстановяване
Примерна ръчна команда (само от доверена, защитена машина):
```bash
pg_dump --format=custom --no-owner --no-privileges --file=moneypilot-backup.dump "$DATABASE_URL"
```
Проверка на архив:
```bash
pg_restore --list moneypilot-backup.dump
```
За възстановяване използвай **отделна празна тестова база**, а не активната продукционна база:
```bash
pg_restore --no-owner --no-privileges --dbname="$RESTORE_DATABASE_URL" moneypilot-backup.dump
```
Тествай рутинно възстановяване. На този етап **няма автоматизиран график за архивиране**, мониторинг или доказано възстановяване. Free Render PostgreSQL няма managed backups.

## Сигурност
Не записвай истински `DATABASE_URL`, пароли, JWT или JSON експорти в GitHub. Ползвай Render Environment secrets. Достъпът до данни изисква валидна потребителска сесия, но предстоят security review, защита срещу brute-force, GDPR и тест за възстановяване. Не използвай финансови данни на реални клиенти, докато тези проверки не са завършени.

## Критерии за готовност
Постоянна платена база; запазване на данни след redeploy/restart; сигурно мигрирани потребители; съхраняване/възстановяване на резервни копия; проверки на права; тестове без регресия; потвърден разход.
